# P0: Replayable editing evidence

## Scope
Persist the complete local editing history, verify its hash chain, and recompute segment provenance and commit metrics without trusting cached scores. Keep the existing rule-based-v0.1 scoring and Git evidence publication flow. P1, remote checkpoints, timestamp authorities and Merkle aggregation are excluded.

## Format and replay
Use an append-only UTF-8 JSONL journal in VS Code global storage, outside the repository. A versioned header contains a random log ID, algorithm and UTF-16 offset convention. Its canonical SHA-256 hash is the genesis tip. Each event binds seq, prevHash, timestamp, file, kind, beforeHash, edit and afterHash; eventHash hashes the canonical event without eventHash. Persist baseline text, exact edits, external reconciliations, saves and session boundaries. Baselines are always unverified. Replay applies validated events to a fresh EditingEngine and never accepts stored scores. Keep only a bounded recent-event view for the UI.

All mutations go through the journal. Restore engine state by replay, including cut/move and nearby-edit history. A restart closes any unfinished session before remaining paused. Retain legacy storage untouched, but do not import legacy scores with missing events. A malformed/truncated journal or write failure blocks recording and receipt issuance, preserving evidence for inspection. Acquire a process lock to prevent concurrent writers; dead-process locks may be recovered.

## Receipt and verification
Retain receipt/v2 with an optional signed eventLog commitment (schema, logId, eventCount, tip, algorithm); session.auditTip must match. Existing receipts remain signature/content-only. Commit metrics use the exact commit manifest: only files whose replayed text exactly equals committed content inherit provenance. Untracked, partially staged, or mismatched files count as unverified. New receipts are computed from a separate replay of the persisted prefix before signing.

A standalone Node CLI takes repository, receipt, public key and journal paths. It verifies signature, target code manifest, chain prefix and recomputed metrics, and returns file reports plus segment offsets/scores/origins without printing source text. A later valid journal suffix is allowed. Missing/truncated prefixes, altered hashes, unsupported versions and metric differences fail. A journal alone demonstrates internal consistency, not authorship or a trusted creation time.

## Privacy and compatibility
Only the receipt, public key and existing summary go to pohw-evidence. No full event log, baseline source or edit text is published. Report the exact local journal path. Public badge verification explicitly says scores were not recomputed. Journals may contain deleted code and secrets; sharing remains a manual user action. No automatic log pruning. Storage grows with baseline content and edits; synchronous append uses OS persistence, with fsync before receipt issuance. Host/power failure may leave a partial line, which is rejected rather than repaired silently.

## Acceptance
Replay >1,000 edits, move operations, Unicode UTF-16 edits, external writes, saves and restarts with identical segment state and metrics. Reject event modification, deletion/reorder/duplication, bad ranges, mismatched before/after hashes, wrong log identity, signed metric fabrication and incomplete journal prefixes. Exercise legacy migration, disk write failure and concurrent writers. Existing tests and VSIX packaging must pass.
